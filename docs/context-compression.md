# 上下文压缩实现、数值依据与验证

## 已实现

图片中的用户诉求保留、分场景记录和同问题聚合已接入运行流程。MemoryService从完整当前会话消息投影场景，保存对象、诉求、条件、显式约束、已尝试方法及结果、来源与状态。助手提出的排查方案单独记录为尚未执行或核验的建议，并保存来源，不能当成用户已执行的尝试。寒暄不生成任务；同对象、同操作、同有效条件与约束的重复问题聚合并累计出现次数。不同订单不聚合。更正后旧场景标为superseded并保留关系，不作为当前有效诉求。

未完成场景和当前结构化对象是必要上下文。用户明确说问题解决后可以归档，但user_resolved仅表示用户对话状态，不能证明订单取消、审批或退款成功。助手的成功话术不能关闭场景。显式“顺便、同时、另外、并且”分隔的复合诉求分别保留。返回旧商品场景时，可根据有来源的场景条件恢复激活信息，供HyDE前指代补全。

场景投影以规则实现，没有新增LLM摘要调用。它覆盖已编码的电商意图和条件，并非通用自然语言摘要：任意隐含诉求、型号、无连接词的复杂复合句或未编码条件仍可能未被提取。匹配到的否定/预算/用途等约束和已尝试结果保存完整相关语句，不固定截断成关键词。原始消息完整保留，可按来源重新核验。

SQLite的conversation_summaries增加scene_signature和scenes_json，迁移为20261014_12。缓存完整来源列表；签名变化重建。当前暂未保存的轮次只在本次上下文投影，不持久化到场景缓存。缓存可以在下一轮从已保存消息重建，重启不依赖旧模型摘要。旧summary方法仍保留兼容，但新build_context不再将逐条截取的旧摘要作为在线摘要。

模型调用前统一计数，包括常驻/领域指引、记忆、最近消息、工具调用参数、工具返回与工具定义。同步、异步、流式、异步流式ModelClient入口均检查；意图识别和需求理解的直接结构化模型入口另行检查。领域循环与汇总入口也检查，支持替身测试。

接近阈值时先删除完全重复的知识正文，再移出可选归档/历史资料，最后删除完整的旧对话轮次。当前问题、常驻规则、未完成诉求、对象来源、待澄清原始请求，以及当前模型工具调用链不可删除。保留sources中的知识全文与条件，不截断政策。依赖与汇总的结果正文也去掉answer_context与sources的完全重复内容，不修改持久化原始结果。必要内容仍超限时拒绝模型调用，向用户说明需要拆分诉求或调整预算。

## 所有预算数字的依据

这些是工程初始配置，尚未通过真实模型对照优化；不是模型厂商规格，也不是宣称最优值。

| 配置或数字 | 当前值 | 依据与计算 |
| --- | ---: | --- |
| 应用上下文窗口 | 16384 | 选择一个可配置的16×1024预算作为初始上限，便于客服控制提示大小；不是当前模型官方窗口，部署者须结合模型能力设置 |
| 输出预留 | 2048 | 初始为总预算的1/8，为结构化任务结果与客服回复保留空间；同时传给ChatOpenAI的max_tokens限制输出；未证明满足所有回答长度 |
| 协议与计数误差预留 | 1024 | 初始为总预算的1/16，用于未计入本地序列化的协议开销与模型分词差异；不能保证抵消所有第三方模型误差 |
| 可用输入预算 | 13312 | 16384−2048−1024 |
| 压缩触发比例 | 0.8 | 在可用输入预算使用80%时开始压缩，提前留出20%余量；启发式策略，不是评测得出的最优阈值 |
| 默认触发点 | 10649 | int(13312×0.8)，向下取整；触发后若必要信息超过此软阈值但未超过输入硬预算，仍可发送 |
| 本地编码 | cl100k_base | 使用tiktoken公开BPE编码，对规范化请求JSON进行可重现计数；第三方聊天模型未必使用该编码 |
| 最近历史候选 | 12条 | 沿用原项目配置，供压缩器选择最近对话，不代表Token上限；本轮当前问题另保留 |
| 场景提示来源 | 首、末来源 | 提示只展示来源端点及每项关键事实来源，完整source_ids存在缓存，降低重复来源列表占用；不是只保留两条原始消息 |
| 新增摘要模型调用 | 0 | 场景投影与压缩均为本地确定性处理；正常聊天及HyDE模型调用仍存在 |

tiktoken的编码方法参考[官方仓库](https://github.com/openai/tiktoken)。实现将消息角色、正文、工具参数和工具定义转换为紧凑JSON再编码。这是本地BPE代理测量，**不是服务端的输入Token、计费Token或实际模型窗口保证**。现有telemetry继续仅采用服务端usage_metadata记录真实用量。日志context.budget提供estimated_before、estimated_after、input_budget、trigger_budget、encoding、删减数量及预留值，可逐次审计。

## 固定实验与每个样本数字的来源

脚本：`backend/scripts/evaluate_context_compression.py`。

```powershell
cd backend
uv run --no-cache python -m scripts.evaluate_context_compression
```

结果在[evaluations/context-compression-2026-10-14/report.md](evaluations/context-compression-2026-10-14/report.md)，完整记录在同目录report.json。它包含请求哈希、源代码哈希、预算、场景及压缩后请求，输入由脚本重建。

| 实验设置 | 数字 | 依据 |
| --- | ---: | --- |
| 实验窗口 | 4096 | 人工设为默认窗口的1/4，以较小预算验证压缩；不是生产建议 |
| 实验输出预留 | 512 | 保持总预算1/8，与默认比例一致 |
| 实验协议预留 | 256 | 保持总预算1/16，与默认比例一致 |
| 实验输入预算 | 3328 | 4096−512−256 |
| 实验触发点 | 2662 | int(3328×0.8) |
| 合成寒暄轮次 | 40 | 人工构造足够多旧轮次，验证裁剪与场景保留；每轮包含用户与助手消息，不是40位用户 |
| 每条寒暄短句重复次数 | 200 | 人工放大消息长度，强制远超预算；这不是正常客服流量分布 |
| 额外重复问题 | 20 | 专门检查同对象同条件聚合；来源不同但不应创建20个独立诉求 |
| 知识规则重复次数 | 50 | 放大sources/answer_context重复正文，验证精确去重且保留条件全文 |
| 超限申请原因重复次数 | 5000 | 验证不可裁剪的当前问题/申请原因超过预算时拒绝发送，而非静默截断 |
| 案例数 | 7 | 脚本显式定义重复、不同订单、更正、排查切换、归档、工具证据、必要信息超限七个案例 |

每行压缩前后数字是对相同编码与同一工具定义的本地计数。减少量可以计算为before−after，减少比例为(before−after)/before；超限拒绝没有压缩后已发送Token，不填0。所有案例以刻意冗长的合成数据进行压力验证，不能外推真实客服压缩率、耗时、任务成功率或费用节省。

## 自动化测试与范围

### 压缩比例配对对照（2026-10-14）

新增脚本`backend/scripts/evaluate_context_thresholds.py`，在backend目录运行`.venv/Scripts/python.exe -m scripts.evaluate_context_thresholds`可重现。[阈值对照报告](evaluations/context-thresholds-2026-10-14/report.md)及同目录report.json记录全部结果、相同输入哈希和源代码哈希。

使用生产默认预算16384−2048−1024=13312，比较50%、60%、70%、80%、90%五种启发式候选。候选以10个百分点间隔覆盖较早到较晚压缩，是实验选点而非已有最优值。原6类正常案例分别将寒暄短句重复1、5、200次，再加1类必要信息超限，共6×3+1=19个不同输入；每组相同输入，共19×5=95次配对检查，全部通过。各比例均18个输入发送、1个按预期拒绝；均值只计算18个发送输入。另3项检查覆盖before小于、等于、大于触发点，全部通过；这些极小比例仅为精确边界探针，不是部署候选。

此次22项专项回归再次通过。该实验不调用在线模型、不修改运行默认比例；工具参数使用search_products定义，未覆盖所有领域工具组合。输入为合成数据且一次性请求，不代表真实会话长度分布或长期压缩频率。各比例均8个可发送输入触发压缩，说明本组长度档位对触发频次区分不足；不能据此选出最优值。更低比例删除更多原始历史、降低本地输入计数，但必要场景正文保留不等于回答语义完整。下一步须使用代表性多轮数据和有效模型配置比较回答质量，80%仍为工程默认值。

本次完整后端运行375个测试项目，全部通过；其中22个来自新增的上下文压缩测试文件，是375的子集。计数来自同目录pytest.xml中的testcase节点，机器可读汇总见[evaluations/context-compression-2026-10-14/validation-summary.json](evaluations/context-compression-2026-10-14/validation-summary.json)。固定实验7个案例全部满足脚本断言，其中6个完成压缩，1个按预期拒绝超限请求；分母是人工定义的案例数，不是线上请求成功率。

`tests/test_context_compression.py`覆盖同对象聚合/不同订单隔离、条件更正与来源、排查结果、场景切换、用户归档与助手伪成功、复合诉求、缓存重启/失效/失败轮次、长历史压缩、完整工具链、原始证据不变、必要信息超限拒绝、各模型调用入口、工具定义预算、显式约束与否定、HyDE前条件恢复和可选归档优先移除。参数化入口会分别计为测试项目，实际数量以pytest运行结果为准。

此前商品错误状态测试使用已经合法的动态分类作为非法参数，已改用limit=0（现有契约要求limit≥1），继续验证固定错误码和异常脱敏；新增未知分类成功返回空结果的回归。这是测试契约更新，没有禁止管理员新增分类。

没有运行在线模型长对话质量对照；此前模型服务有401鉴权错误。当前结果证明这些合成案例的确定性不变量通过，不证明模型压缩后一定理解正确。完整线上任务成功率、实际输入/输出Token差异、计费节省和延迟变化仍需有效模型配置及人工标注集。
