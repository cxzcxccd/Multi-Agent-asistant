# 客服上下文分层

## 运行路径

会话服务从数据库读取当前买家的当前会话，组装本轮用户消息，记忆服务在裁剪历史前投影出结构化会话对象。Router使用补全后的问题做路由，Supervisor与需求理解读取结构化对象，领域Agent按任务加载独立指引，工具依照后端身份与规则执行。知识工具只将必要对象与条件加入检索问题，再进入BM25、向量与HyDE。

## 三层组成

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 常驻规则 | `backend/app/ai/prompts/resident.md` | 客服职责、事实依据、权限、确认审批、不确定性与回复方式 |
| 按领域加载 | `backend/app/ai/prompts/skills/*.md` | 商品、订单、售后、知识、通用任务各自的步骤与工具要求 |
| 动态参考 | `backend/app/ai/context.py`及现有MemoryService | 会话对象、消息来源、确认状态、偏好、旧消息摘录、按需历史结果与最近对话 |

这些领域指引是应用内部的任务提示文件，不是桌面Codex技能，也不具备额外权限。平台规则继续从版本化知识库检索，不写死为平台常量。旧`customer_service.md`保留给兼容的单Agent路径；多Agent运行采用新常驻文件与领域指引，汇总也遵守常驻约束。

## 结构化对象与来源

保存当前订单、SKU、商品类别和激活条件。每个字段携带用户原话证据、消息ID、来源时间（若有）、候选值、`user_explicit`或`ambiguous`状态。`business_verified`始终为false，明确提及不代表数据库归属核验，也不是写操作确认。

买家身份和会话ID由后端已经核验的会话提供，不从消息提取。只扫描当前会话用户消息，助手回复、显式购物偏好和其他会话历史不能生成当前操作对象。另一个买家或新会话不会继承对象。

这是确定性的消息投影，不另外建立可漂移的状态表。原始消息已持久化，每轮从当前会话完整用户历史重建，故重启后可恢复、超过最近12条窗口也不丢来源。当前未保存成功的用户轮次不会成为下轮持久记忆；原始消息修订会在下一次投影时反映。

当前实体识别是保守规则：显式五位订单号、带SKU/商品编号标记的商品ID、项目支持的商品类别与明确激活状态。不覆盖任意自然语言实体识别。未建立跨会话默认订单、业务事实缓存或按时间自动过期的用户指代状态；旧对象只是线索，实时业务状态每次查工具。显式“换个话题”等会清空对象，新的订单、商品或SKU会清除相应旧条件。

## 多轮与操作边界

- “查订单10002”后问“这单到哪了”：订单号来自原用户消息，查询仍校验归属。
- “不是订单10002，是10003”：只保留更正后的对象，实体提取和任务槽位不会继续使用旧编号。
- 上文同时出现两件商品或两笔订单，当前问“它/这单”：追问具体对象，不取第一条。
- “耳机未激活”后问“那拆封了呢”：知识问题补为当前耳机与未激活条件下的拆封问题。买家ID、摘要和整段历史不会传入HyDE。
- 旧摘要称已退款：不能作为到账状态；必须重新查售后业务。
- 用户更正订单或申请内容不会自动提交或复用旧确认；已有草稿页面确认与后端检查点恢复继续负责写操作。

知识工具通过每次LangGraph工具调用的RunnableConfig取得当前结构化上下文，不用全局可变状态。并行任务和不同会话各自传参，已验证并行知识调用不串商品对象。无法解析时返回`AMBIGUOUS_REFERENCE`，不调用检索或HyDE；开发者可从工具记录查看原问题、补全后的问题和错误。

## 范围与验证

最近对话、摘要和按需历史检索仍沿用既有有界策略；结构化对象只保留必要字段与每项最多200字符原话证据。不依赖LLM生成摘要来认定订单或执行授权，不新增模型调用。领域指引增加一个小的系统消息，但避免每个领域都携带完整售后、订单和知识操作说明。

回归覆盖来源、更正、否定、多对象、跨买家隔离、历史裁剪后的槽位补全、HyDE前指代解析、知识工具并发隔离和领域加载。不能据此宣称理解了所有指代、降低了实际Token或提高了任务成功率；真实效果需独立评测。
